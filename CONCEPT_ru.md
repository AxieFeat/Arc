# Введение
**Arc Engine** - это гибкий 3D/2D графический движок, разработанный с учетом независимости от реализации,
что позволяет ему работать практически с любой технологией и платформой.

## Зачем?
Он создан для разработчиков, которые хотят прописывать всю логику самостоятельно, а не тянуть тяжелые фреймворки.

В отличие от остальных движков - Arc максимально простой и предоставляет базовые обертки над графическим API.
Однако для более низкого порога вхождения отсутствует возможность детальной настройки графического конвейера.

Однако простота Arc не обозначает легкость в использовании. Хоть его и нельзя назвать
низкоуровневым - необходимо знать базовые концепции в работе компьютерной графики.

## Идея
Главная идея проекта - максимально абстрагироваться от **конкретных графических API** (OpenGL, Vulkan, Direct3D)

Мы не пишем код под графическое API - мы делаем **универсальную прослойку между разработчиком и графическим API**.
Это позволяет не зависеть от API и платформы, на которой приложение запускается.

То есть мы имеем одну универсальную Arc API, которая позволяет писать универсальный код под все платформы
и графические API.

# Философия движка

Движок **не подразумевает прямое использование методов графических API и прочих внутренних реализаций**, по этой причине все реализации
являются **internal** классами. Пользователь может использовать **только функционал API модулей движка Arc**. Использование
внутренних реализаций крайне нежелательно и будет противоречить главной концепции движка.

### Структура проекта

Проект состоит из API модулей - они представляют собой интерфейсы, которые в последствии реализуются другими
модулями. Важно, что API в таких модулях является обобщённой и подходит под любую технологию рендера.

> У каждого **API модуля** обязательно есть как минимум одна реализация.
> Реализации есть двух видов:
> - **Базовая** - мы все ещё не отсылаемся на какие-либо конкретные наименования и библиотеки. Мы пишем реализацию, которая будет универсальной для всех последующих **бекендов**.
> - **Бекенд** - конкретная внутренняя реализация, которая чаще всего будет зависеть от **базовой** - здесь используются конкретные библиотеки и наименования.
>
> > То есть весь проект придерживается структуры вида:\
> > **API** -> **Базовая реализация** -> **Бекенды**
>
> Важно, что части бекенда не должны просачиваться в API - **Это противоречит философии движка.**

API абсолютно всегда должно оставаться обобщенным.
Из-за этого **низкоуровневые API (Vulkan, Metal и т.д.)** получают куда меньший функционал - мы подстраиваемся под самую высокоуровневую библиотеку.
Иначе функционал, который возможен на Vulkan - не получится реализовать на других бекендах из-за высокоуровневости.
